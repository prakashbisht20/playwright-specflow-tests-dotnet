Playwright SpecFlow Tests - .NET

A UI test automation framework built with Microsoft Playwright, SpecFlow, and .NET for writing and executing maintainable end-to-end tests using BDD (Behavior-Driven Development).

Overview

This project combines:

Playwright — Reliable browser automation and end-to-end testing.
SpecFlow — BDD framework for writing tests in Gherkin syntax.
.NET — Application platform and test runtime.
Gherkin — Human-readable feature files describing application behavior.

The framework is designed to keep test scenarios readable while providing reusable page objects, step definitions, and test infrastructure.

Prerequisites

Make sure the following are installed:

.NET SDK
Git
A supported browser installed through Playwright

Verify the .NET installation:

dotnet --version

Getting Started
1. Clone the repository
git clone <repository-url>
cd playwright-specflow-tests-dotnet

2. Restore dependencies
dotnet restore

3. Install Playwright browsers

After restoring the project dependencies, install the Playwright browsers required by the test suite.

For example:

pwsh bin/Debug/net*/playwright.ps1 install


On Linux/macOS, you may need:

./bin/Debug/net*/playwright.sh install


If your project uses a different Playwright installation approach, follow the setup generated by the project's Playwright package.

Writing Tests

Tests are written using Gherkin feature files.

Example:

Feature: Login

  Scenario: Successful login
    Given I navigate to the login page
    When I enter a valid username and password
    And I click the login button
    Then I should be redirected to the dashboard


The corresponding step definitions connect the Gherkin steps to Playwright actions:

[Given("I navigate to the login page")]
public async Task GivenINavigateToTheLoginPage()
{
    await _page.GotoAsync($"{_baseUrl}/login");
}

Page Object Model

Application interactions should preferably be encapsulated in page objects rather than directly implemented in step definitions.

Example:

public class LoginPage
{
    private readonly IPage _page;

    public LoginPage(IPage page)
    {
        _page = page;
    }

    public async Task LoginAsync(string username, string password)
    {
        await _page.GetByLabel("Username").FillAsync(username);
        await _page.GetByLabel("Password").FillAsync(password);
        await _page.GetByRole(AriaRole.Button, new() { Name = "Login" }).ClickAsync();
    }
}


This keeps step definitions focused on behavior and makes UI interactions easier to maintain.

Running Tests

Run the complete test suite:

dotnet test


Run tests without rebuilding:

dotnet test --no-build


Run a specific test by name:

dotnet test --filter "FullyQualifiedName~Login"


If your project defines SpecFlow tags, tests can also be filtered by category/tag depending on the configured test runner.

Test Configuration

Environment-specific values should not be hard-coded into feature files or page objects.

Typical configuration values include:

{
  "BaseUrl": "https://example.com",
  "Browser": "chromium",
  "Headless": true
}


For CI/CD environments, prefer environment variables or secure pipeline variables for credentials and other sensitive configuration.

Example:

BASE_URL=https://test.example.com


Never commit passwords, access tokens, API keys, or other secrets to source control.

Best Practices
Feature Files
Keep scenarios focused on business behavior.
Use descriptive scenario names.
Avoid putting implementation details into Gherkin.
Reuse common steps where they improve readability.
Step Definitions
Keep step definitions concise.
Avoid duplicating UI interaction logic.
Delegate browser interactions to page objects.
Avoid hard-coded waits such as Task.Delay().
Page Objects
Keep selectors centralized.
Prefer accessible locators such as roles, labels, and text where appropriate.
Keep page objects focused on a single page or logical component.
Avoid exposing unnecessary Playwright implementation details to feature files.
Tests
Make tests independent.
Avoid relying on test execution order.
Use deterministic test data.
Clean up created test data when appropriate.
Capture useful diagnostics when failures occur.
Recommended Locator Strategy

Prefer resilient locators:

await page.GetByRole(AriaRole.Button, new() { Name = "Submit" }).ClickAsync();


or:

await page.GetByLabel("Email").FillAsync("user@example.com");


Avoid fragile selectors based on deeply nested CSS or generated element IDs whenever possible.

Troubleshooting
Playwright browsers are missing

Install the required Playwright browsers again:

pwsh bin/Debug/net*/playwright.ps1 install

Tests cannot find the application

Verify the configured BaseUrl and ensure the target environment is accessible from the machine or CI runner.

Tests are flaky

Check for:

Unstable selectors
Race conditions
Missing application state setup
External service dependencies
Shared test data
Tests depending on execution order

Avoid arbitrary sleeps. Prefer Playwright's built-in auto-waiting and explicit assertions.
